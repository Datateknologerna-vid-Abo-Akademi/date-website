# Attendance Development Notes

## Responsibility
The `attendance` app owns the digital meeting attendance list: an event gets a public check-in page, and the app records who arrives and who leaves, so a meeting can stop passing a paper list around. Events are created in the Django admin, and a participant checks in with a short code that the site shows to staff and rotates.

The app is installed for the `date` variant only: `core/settings/date.py` lists `attendance` in its `get_installed_apps([...])` call, and no other `core/settings/<variant>.py` does. It has no capability flag of its own. `core/urls/date.py` passes the `attendance` route key to `build_urlpatterns(...)` unconditionally, next to `booking`, which is mounted only when `settings.BOOKING_ENABLED` is true. Removing attendance from a release would be a code change, not an environment variable.

Access is not a permission of the app either. The overview page and the websocket both test `user.is_staff`, and `members.Member.is_staff` is membership of a group named in `settings.STAFF_GROUPS` (for `date`: `styrelse`, `admin`, `fotograf`, `rösträknare`) or a superuser. Every one of those groups can therefore read the current code and the change log. That is wider than "the board", and it is the app's main access limit.

## Models
`attendance/models.py` defines everything, in four models.

- `AttendanceEvent`: `title` (max 255), `description` (max 255, optional), `start_datetime`, optional `end_datetime`, `allow_non_members` (default `False`, so a new meeting is members-only until an editor ticks the switch), `code_secret` (default `django_otp.util.random_hex`), `code_validity_time` (a `SmallIntegerField`, default 30 seconds), and a unique `slug` (max 50, `allow_unicode=False`, so the URL segment is ASCII).
- `NonMemberAttendee`: a single `name` field (max 255, unique), and a `UniqueConstraint` on `Lower("name")` named `unique_non_member_name_ci`, so the folded name is unique too. It has no link to an event, which is what makes a guest one shared row. See Non-member identity.
- `AttendanceChange`: `event` (FK to `AttendanceEvent`, `on_delete=CASCADE`, `related_name="attendance_changes"`), nullable `user` (FK to `AUTH_USER_MODEL`, CASCADE), nullable `non_member` (FK to `NonMemberAttendee`, CASCADE), `timestamp` (default `django.utils.timezone.now`), and `type` (`Type.ENTER = 0`, `Type.LEAVE = 1`). A check constraint named `foreign_keys_ok` requires exactly one of `user` and `non_member` to be set: a change is about one attendee of one kind, never both and never neither. `Meta.get_latest_by = "timestamp"` and `Meta.ordering = ["-timestamp"]` put the newest change first in every list: the inline at the bottom of an event's admin page, the standalone change list, and the "Närvaroändringar" log on the event page. `attendee_label(attendee)` in `attendance/models.py` is the one definition of an attendee's name, and it is deliberately untranslated: a member's `get_full_name()`, and for a guest the bare `name`. `AttendanceChange.attendee_name` returns it, which is the label the websocket payload carries and the staff overview page displays; the identity the page matches on is `attendee_key`, described next. A guest's `get_full_name()` is `NonMemberAttendee.__str__`, the name plus a translated "(icke-medlem)" marker; that marker is fine on the event page, whose change log renders in one language, but it cannot be part of a label that has to match between a participant's request and a staff member's browser.
- `AttendancePoll`: `question` (a `OneToOneField` to `polls.Question`, `on_delete=CASCADE`, `related_name="attendance_poll"`) and `event` (a `ForeignKey` to `AttendanceEvent`, `on_delete=CASCADE`, `related_name="polls"`). It is the per-poll opt-in for room-only voting: a poll with a row here accepts a vote only from somebody `is_attendee_present` finds in the room, and a poll without one is an ordinary poll with the vote rules it always had. The one-to-one says a poll belongs to at most one meeting, while one meeting can carry several polls. The field is declared with the string target `'polls.Question'`, not an import, for the reason the class docstring gives: every association installs `polls` and only `date` installs this app, so the reference has to stay lazy and one-directional. `polls` reads the link back through the accessor the field creates, `Question.attendance_poll`, behind `apps.is_installed('attendance')`; the vote path itself is in `docs/dev/polls.md`.

`attendee_key(attendee)` is the identity beside that name: `user-<pk>` for a member and `non-member-<pk>` for a guest. The two kinds are namespaced because they are different tables, so their primary keys are not comparable. The name cannot serve as the identity: two members can share one, and a guest can type one that a member already has. `attendee_entry(attendee)` returns `{"key": <key>, "name": <label>}` for one row of the staff list, and `AttendanceChange.attendee_key` exposes the same key for a change, which is what the broadcast carries. The page, the connect snapshot and the broadcast all build their entries through `attendee_entry()`, so an attendee has one key everywhere.

Presence is never stored. `AttendanceEvent.present_attendees(timestamp)` answers who was in the room at that moment: it considers only changes at or before the timestamp, and returns the attendees whose newest one is `ENTER`. `is_attendee_present(attendee, after_timestamp)` answers a different question about one attendee, whether that person's newest change (or newest change since `after_timestamp`, when it is given) is an entry, so with a timestamp it is a check on the recent past rather than a snapshot at a moment. `polls/vote.py` is now the caller that gives the method a second job outside this app: it asks `AttendancePoll.event.is_attendee_present(user)` with no timestamp, which is "is this member in the room right now", before a vote on an attached poll is counted. `was_attendee_present` asks whether somebody ever entered, and still has no caller outside its tests. `present_count(timestamp)` is the same question as `present_attendees` answered as a number, and it is the version that works everywhere: it walks the event's changes newest first and keeps the first row per attendee itself, so it needs neither the `distinct("user", "non_member")` that only PostgreSQL understands nor a query per attendee. The two pages do not call it, because both already render the list and their number is that list's length; `polls/admin.py` does, because there only the number is wanted. `is_attendee_present` reads `.latest()`, which uses `Meta.get_latest_by`; `present_attendees` instead asks the database for the newest row per attendee (see The PostgreSQL-only presence query).

`has_ended` is a property that is true only when `end_datetime` is set and already past. Nothing in the app reads it. What filters the public list is the queryset in `attendance/views.py`: an event with an end is listed while `end_datetime >= now()`, and an event with **no** end only while `start_datetime > now() - NO_END_LISTING_HOURS`, which is 24 hours. A meeting that recorded an end therefore leaves `/attendance/` as soon as that moment has passed, and one whose end nobody filled in leaves it a day after it started, so a forgotten end cannot pin yesterday's meeting to the public page for ever. The bound is on the list and nothing else: the detail view consults neither the filter nor `has_ended`, so an event's page, its code and its QR code keep working after the end and after that day for anyone who still has the URL or the QR code. The filter is presentation, not a lock.

## Forms & Views
`attendance/forms.py` is one form, and it renders nothing: `AttendanceChangeForm` carries `non_member_name` (optional, max 255), `type` (a typed choice field) and `code` (optional `IntegerField`). It exists so the POST is validated; the template owns the markup.

The views subscript a generic at class-definition time (`SingleObjectMixin[AttendanceEvent]`), which is a runtime expression and not only a type annotation. `core/settings/common.py` calls `django_stubs_ext.monkeypatch()` at import time for exactly that, and `django-stubs-ext` is a runtime dependency in `pyproject.toml`. Dropping either one breaks the module at import.

`attendance/urls.py` declares three names, and `core/urls/common.py` mounts the app under `attendance/`:

- `attendance-index` at `/attendance/` (`AttendanceEventsView`): public, no login. It lists the events the queryset above leaves, soonest first, each linking to its slug, so the meeting that is running now is at the top. Nothing in the code puts this page in the site's menus: the menu is editor content, so a link is added through the admin's navigation (a Static Page Nav category or a Static URL entry) like any other link, and it disappears again if an editor removes it.
- `attendance-event-view` at `/attendance/<slug>/` (`AttendanceEventDetailView`): public when `allow_non_members` is true, and that field defaults to `False`, so a new meeting is members-only until an editor ticks the switch. When it is false the view runs behind `UserPassesTestMixin`, so an anonymous visitor is redirected to the login page (`LOGIN_URL = "members:login"`) while any signed-in member gets in. The mixin redirects with `self.request.get_full_path()`, so the `?code=` the visitor arrived with rides along in `next` and logging in lands back on the check-in page with the room's code filled in. An unknown slug is a 404.
- `attendance-event-overview` at `/attendance/<slug>/overview` (`AttendanceEventOverview`, note the missing trailing slash): staff only, again through `UserPassesTestMixin`. Anonymous is redirected to the login page, and a signed-in member who is not staff gets 403.

The detail POST answers with four status codes:

- 403 when the form does not validate, and 403 with the message "Fel kod" when `is_code_valid` rejects the code. An anonymous POST with an empty name is 403 too, with "Namn måste anges om du inte är inloggad", although the template marks that input `required` and a browser never sends it empty. A malformed `type` is also 403: it is the one form error for a field the page does not draw, so the view maps `type_error` onto `generic_error`, which the template renders, rather than failing silently.
- 409 when the request contradicts the log: "Du kan inte gå in i ett evenemang var du redan är närvarande" for an `ENTER` while the attendee is already present, and "Du kan inte gå ut ur ett evenemang var du inte är närvarande" for a `LEAVE` while they are not.
- 429 while the session is locked out after too many wrong codes, including the submission that reaches the limit. The page shows how long is left and the submission writes nothing, even when the code in it is correct.
- 303 on success, to the `next` parameter when it names a safe local URL and to `request.path` (the same page without the `?code=` the QR code added) otherwise. The response uses the local `HttpResponseSeeOther`, because `HttpResponseRedirect` is 302.

### The `next` parameter
A participant can arrive here from a room-only poll, which refuses a vote until they are in the room and links to this page with `?next=/polls/<id>/` (see `docs/dev/polls.md`). The detail view reads that value on GET from the query string and on POST from the form, and `_safe_next()` accepts it only when `django.utils.http.url_has_allowed_host_and_scheme` allows it against `request.get_host()`: a value with another host, including the `//evil.example` shape and a full `https://evil.example/polls/7/` URL, is dropped and the 303 falls back to `request.path`. That check is the open-redirect guard, and the value is dropped rather than reflected, so the page never renders a hostile URL. A safe value is rendered into the check-in form as a hidden input, and that is what carries it through a refused attempt: the 403 for a wrong code, the 429 for a lockout and the 409 for a conflicting change all render the page again through `get_ctx()`, and the hidden input is still there for the attempt that succeeds. The field is absent when there is no `next`, and the QR flow's `?code=` is read from the query as before, so the two parameters coexist in one URL.

The write is deliberately not atomic. A comment in `views.py` accepts that two simultaneous submissions can both pass the presence check and write two rows, "but it wouldn't really matter in the end": presence is read from the newest row, so the answer is unchanged. Unlike `booking`, there is no `select_for_update` here, and the duplicate stays in the log.

After the row is saved, the view calls `websocket.send_attendance_change(...)` with no error handling around it. A channel-layer failure (Redis unreachable) therefore surfaces as a 500 after the change has already been written. Pressing the button again then gets the 409, so no second row is added.

### The remembered guest name
A guest who has no account types their name on every visit, so the view keeps the last one in a cookie. A successful anonymous change, meaning one that wrote an `AttendanceChange`, sets `attendance_non_member_name` on the 303 response to the name that was typed, with `HttpOnly`, `SameSite=Lax`, `path="/"`, `secure` when the request is secure, and a `max_age` of one year. The two values are `NON_MEMBER_NAME_COOKIE` and `NON_MEMBER_NAME_COOKIE_MAX_AGE` in `attendance/views.py`. The name is percent-encoded into the value and decoded again on the way in. That is not decoration: a `Set-Cookie` header is latin-1, and `http.cookies` escapes a name like "Gäst" into `G\344st`, which a browser hands back verbatim and Django then drops as an unparseable cookie, so an unencoded cookie would silently lose exactly the Swedish names this site is made of, and a name outside latin-1 would break the header outright. A refused attempt sets nothing: the 403 for a wrong code, a missing name or a malformed form, the 429 for a lockout and the 409 for a conflict all return before the cookie is written. A member's successful change writes nothing either, because a member is identified by the account and not by a name box.

On a GET the view reads the cookie back. It prefills the name input with the value in `prefilled_name`, and it resolves the name with `NonMemberAttendee.objects.filter(name__iexact=...)`, so a remembered guest gets the treatment a member gets: the line that says whether they are present, and the button that makes no sense disabled. The match is case-insensitive for the same reason the check-in is: the row keeps the spelling used first while the cookie keeps the spelling typed last, so an exact lookup would lose a guest who typed their name differently the second time. Nothing is created on a GET. A cookie is a claim about a name, not a guest, and `get_or_create` stays where it was, on a submitted check-in, so a cookie naming nobody prefills the box and shows no state.

The cookie is convenience only, and the log does not depend on it. A guest's identity is the name they submit, exactly as it was before this cookie existed: two people who type the same name still share one row, a different name is a different attendee, and clearing cookies costs a guest nothing but retyping. Capitalisation and leading or trailing whitespace are folded by the check-in (see Non-member identity), so a name that differs in either of those is not a different attendee either. `HttpOnly` keeps the name away from the page's scripts, and `secure` is read from `request.is_secure()`, which the deployment's forwarded-protocol handling makes true on an HTTPS request.

### The code
`AttendanceEvent.totp` builds a `django_otp.oath.TOTP` over `code_secret.encode()` with `step=code_validity_time`: the library's standard six-digit SHA1 TOTP. `get_current_code()` returns `totp.token()`, and `is_code_valid(code)` accepts the current period's token or the one before it: `django_otp` verifies the current step only, so the previous period is reached by asking the same secret to count one step back with `drift=-1`. A code that rotates while somebody is typing it therefore still works for one more period, a code two steps old is refused, and the *next* period's code is deliberately not accepted early. That matters now that a handful of wrong codes starts a lockout, because the participant who is a little slow is exactly the one the grace protects. `time_until_next_code()` is `step - totp.time % step`, the seconds left in the window, which is the value the websocket returns to the overview page.

The code is rendered in one place: `AttendanceEventOverview.get_ctx` puts `get_current_code()` into the context of `templates/common/attendance/overview.html`, and the staff websocket serves the same value (see Websocket). No other view or template renders it. That is the anti-abuse control behind issue #398, the requirement that the attendance list cannot be used to inflate a meeting's membership: checking somebody in needs a code that is visible only to staff, on the spot. Its strength is the display and nothing else. The code is six digits, it is shown to everyone in the room, and it rotates every 30 seconds by default, so it is proof of presence at the meeting rather than a credential that identifies a person. Both `code_secret` and `code_validity_time` are editable in the admin, and changing the validity time also changes the step, so the code in force moves at once. The period has a floor of one second: `django_otp` divides by the step, so a zero or negative period breaks the calculation outright, and a `MinValueValidator(1)` on the field is what stops the admin form from saving one.

### The check-in control
The code is the only thing that stands between the public page and the log, and it is a low bar on purpose. `attendance/limits.py` counts wrong codes in the session: after `ATTEMPT_LIMIT` (5) of them the session is locked out for `LOCKOUT_SECONDS` (60), every submission in that window answers 429 with "För många felaktiga koder. Försök igen om N sekunder.", and a correct code clears both the counter and the lockout. The limit is checked before the code is, so a lockout also refuses the right code, which is the point: otherwise an attacker keeps guessing while a participant's correct attempt slips through. The lockout is deliberately short, because the code is on a screen in the room and the likeliest person holding a wrong one is a participant who mistyped it.

What that bounds is worth stating plainly. The counter is in the session, so a client that discards its cookie starts over, and this is a speed bump rather than a wall. Moving it server-side needs a key the client cannot throw away, and the obvious candidate, the client address, is rewritten by the ingress, so every visitor would share one bucket and a low threshold would lock out the whole meeting. `docs/dev/booking.md` describes the same trade-off for the booking code.

The form is validated before the lockout is consulted, so a malformed submission is a 403 that costs no attempt.

## Templates and JavaScript
- `templates/common/attendance/index.html`: the event list under the page's one `h1`, each entry a link to the event page resolved with the `{% raw %}{% url 'attendance-event-view' e.slug %}{% endraw %}` tag.
- `templates/common/attendance/detail.html`: the check-in page. Its one `h1` is the event title, the description is a `<p class="h5">` rather than a heading, and "Till översiktsvyn" is resolved with the `{% raw %}{% url 'attendance-event-overview' object.slug %}{% endraw %}` tag, so the link follows the URLconf rather than a hardcoded relative path. It prints "Börjar:" and "Slutar:" from the event, shows the name input and its explanatory sentence only to an anonymous visitor, with the input prefilled from the name cookie, tells a member and a remembered guest whether they are present (the context's `is_present` is `None` only when the page cannot say, which is a visitor with no account and no remembered name, and then the page draws no state for them), and disables "Gå in" for whoever is present and "Gå ut" for whoever is not. The name input has a short visually hidden `<label>` and points at the explanation with `aria-describedby`; the code input has a visually hidden `<label for="code">` because a placeholder is not a label. Both field errors get an `id`, `role="alert"` and an `aria-describedby` on their input, so a wrong code or a missing name is announced and tied to the control it belongs to. The decorative button icons are `aria-hidden="true"`, and `#qr-reader-error` is `aria-live="polite"` because the script writes into it. "Närvarande" lists the current attendees from the `present_attendees` context, and the heading carries how many there are in a `<span id="present-count">`, the same element the overview page uses; the staff-only "Närvaroändringar" log lists the event's changes newest first, from the `changes` context the view loads with `select_related` so the names cost one query rather than one per row. The "Till översiktsvyn" link appears only when `can_see_overview` is true, the same staff test the overview view makes. A `next` the view accepts is rendered as a hidden input in the check-in form and nowhere else, so a refused attempt keeps the return path; the input is absent when there is no `next`, and an off-site value is dropped rather than drawn.
- `templates/common/attendance/overview.html`: the current code in large digits, a status line, the QR canvas and the `Närvarande` list from the `present_attendees` context. Its one `h1` is the event title, and the code is a `<p class="h1" id="current-code">`, which looks the same without claiming to be the page heading. The `Närvarande` heading carries the number of attendees in that list inside a `<span id="present-count">`, which is the element `overview.js` writes the list's length into. The list has the stable id `present-attendees`, one `<li data-attendee="<key>">` per attendee displaying that entry's name, and an empty-state element that shows when the list is empty. The list, the status line and the empty state all carry `aria-live="polite"`, because the script changes them without a page load and a screen reader would otherwise say nothing about somebody arriving. The page links nowhere, so a staff member reaches it from the event page.

The QR flow, end to end:

1. `static/common/attendance/js/overview.js` renders the event page's address with `?code=` appended into the canvas with the CDN `qrcode` library (`QRCode.toCanvas`). The address comes from the view, which asks `request.build_absolute_uri()` for the `attendance-event-view` route: the address this page is being served from, carried to the template in the `data-event-url` attribute of the `#qrcode` element. In production that is the association's own domain, because the chart deploys with `USE_X_FORWARDED_HOST` and `TRUST_X_FORWARDED_PROTO` on by default (`charts/date-website/values.yaml`) and the ingress passes the public host and protocol through; everywhere else, a QA deployment or a laptop, it is that instance's own address, which is the one a room standing in front of this screen can reach. A `CONTENT_VARIABLES['SITE_URL']` value would name the same domain in production but the wrong instance in those other cases, and `booking/emails.py` reaches for it only because mail is composed where there is no request to ask. The one way to get this wrong is to open the overview page through an internal service name that bypasses the ingress, which would put that name in the code. It has to be absolute: a phone's camera app only offers to open a link, and this page's own scanner parses the value with `new URL()`, which throws on a bare path. Both routes to the page were broken while the value was a path. The URL the view builds is the event page itself, trailing slash included, so a scan does not take a redirect. The websocket URL below is built from `window.location.pathname` with the last segment dropped instead, because its route matches without a trailing slash.
2. A participant scans that code with a phone camera and lands on `/attendance/<slug>/?code=<code>`.
3. `detail.html` writes the `?code=` value into the code input, so the box arrives prefilled. A `?next=` in the same URL becomes the hidden input beside it, so a code that arrives from a poll link survives a mistyped first attempt.
4. `static/common/attendance/js/detail.js` drives the on-screen scanner with the CDN `qr-scanner` library. The "Skanna QR-kod" button starts `disabled` in the template, and the script enables it only after it has constructed the scanner, so a failed CDN load or a browser with JavaScript off leaves a disabled button and a typable code field rather than a dead control. A failed construction is not silent: the script writes "QR-skannern kunde inte laddas" into `#qr-reader-error`, which is why that element is `aria-live`. A device without a camera is a separate case: the button works, and pressing it shows "Ingen kamera hittades". The template's `noscript` block says "Tillåt JavaScript för att skanna QR-koder". A scan parses the URL with `new URL(value, window.location.origin)` inside a `try`/`catch`, so a value that is a bare path rather than a link, which is what a code generated before that fix holds, still resolves against this page and fills the box in (`URL.parse` is a 2024 API and throws on older browsers, which would leave the code empty and the camera running), reads its `code` parameter, writes it into the input and stops the camera; a QR code without that parameter, or one that is not a URL at all, shows "QR-koden innehöll ingen kod". The code field and the two submit buttons are ordinary form controls, so check-in by typing the code still works with JavaScript disabled, and only the camera is lost.
5. The participant still presses "Gå in" or "Gå ut". The code prefills the form, it does not submit it.

`overview.js` keeps the display live: on `open` it sends `{"type": "get_code"}`, and each reply carries `until_next`, the seconds left in the window, which it uses to schedule the next request. The delay is validated before it is used, because a renamed or missing field would make it `NaN` and `setTimeout` treats `NaN` as zero, which would turn the countdown into a tight request loop; `JSON.parse` is wrapped for the same reason, so one unreadable frame does not stop the rotation. A closed socket shows "Anslutningen till servern bröts" and retries after five seconds. The last code it received stays on the screen while the socket is down, and that status line is the signal that it may be out of date: blanking the number would leave the room with nothing to read at all. A close the server meant as final is different, and shows "Sidan kan inte längre uppdateras. Ladda om sidan." without a retry. The first code is rendered by the view, so a page whose CDN script fails still shows a code, it just never rotates. Drawing the QR code is guarded as well, because the QR code is a convenience for phones while the attendee list is the point of the page: a CDN load that leaves `QRCode` undefined must not stop the socket from opening.

The same script consumes the `attendance_snapshot` message sent on connect and the `attendance_change` broadcast, so the staff screen lists who is present without a reload. The snapshot replaces the whole list; entries are keyed, so a snapshot and a live change for the same attendee are idempotent and no ordering between the two messages is needed. An `ENTER` appends a list item for `data.name` unless one with that `data.key` is already there, a `LEAVE` removes the item with that key, and the empty state is shown whenever the list has no items. Every one of those paths also refreshes the headcount in `#present-count`, and the number is read from `attendeeList.children.length` rather than kept in a variable of its own, so the heading and the rows cannot drift apart. The template renders the same value before the socket opens, so a page whose scripts never load still shows the right number. Matching on the key rather than the name is what keeps two people with the same name, or a guest whose name matches a member's, as two rows. The item is built with `document.createElement` and `innerText`, so nothing from the socket is parsed as HTML.

Both scripts call their strings through the `gettext` global injected by the page's `{% raw %}{% url 'javascript-catalog' %}{% endraw %}` script tag, and every user-visible string in them is wrapped. They are the only entries in the `locale/sv|en|fi/LC_MESSAGES/djangojs.po` catalogs: "Ingen kamera hittades", "Ett oväntat fel uppstod medan QR-skannern startades", "QR-koden innehöll ingen kod", "QR-skannern kunde inte laddas", "Ansluter till servern...", "Anslutningen till servern bröts" and "Sidan kan inte längre uppdateras. Ladda om sidan.". The template and model strings are in the ordinary `django.po` catalogs for the same three languages.

## Websocket
`attendance/routing.py` exposes `websocket_urlpatterns` with `re_path(r"ws/attendance/(?P<slug>[-\w]+)/?$", consumers.AttendanceConsumer.as_asgi())`. The trailing slash is optional, so a path variant that ends in one still reaches the consumer. `core/routing.py` holds the `WEBSOCKET_ROUTES` map (`{'events': 'events.routing', 'attendance': 'attendance.routing'}`) and imports an app's routing module only when `apps.is_installed(<app label>)` is true, so a variant that does not install `attendance` never loads its consumer through the socket path.

`AttendanceConsumer` is staff-only, because it also serves the current code: `connect` checks `AttendanceEventOverview.is_user_allowed(self.scope["user"])` and closes before accepting anyone else. Every accepted client is sent `{"type": "attendance_snapshot", "data": [{"key": ..., "name": ...}, ...]}` straight after the accept, holding the attendees who are present at that moment. The page is rendered before the socket opens, so without it anything that happened in between would be lost; entries are keyed, so the snapshot and a live change for the same attendee are idempotent and no ordering between them matters. `connect` also looks the event up, and an unknown or deleted slug closes the socket there rather than raising: an exception would close it too, but the client reconnects every five seconds, and a failure inside `get_code` would keep that loop going against an event that is never coming back. The lookup is repeated per message, so an admin change to the secret or the period reaches an open page at once, and it closes the socket when the event has gone. The authorization is re-checked before every message and before every broadcast is forwarded, because the socket serves the code and must not outlive the permission: a staff member removed from the staff group mid-connection is closed out instead of being handed another code, or another attendee name. Both of those closes, and the ones for a slug that is gone, carry a code the client understands: `4003` for a permission that has gone and `4004` for an event that has gone (`AttendanceConsumer.NOT_ALLOWED` and `.EVENT_GONE`). `overview.js` stops retrying on either of them instead of asking every five seconds for a page that will never answer. It joins the group `attendance_<slug>`, and it answers `{"type": "get_code"}` with `{"type": "code", "code": <int>, "until_next": <seconds>}`. Any other message is ignored.

`attendance/websocket.py` broadcasts every saved change to the same group as an `attendance_change` event, and the consumer forwards it to its clients. `overview.js` is the client: it handles the `code` message, the `attendance_snapshot` and the `attendance_change` broadcast, so the staff overview page shows a live code and a live `Närvarande` list. `detail.js` opens no socket, so the public event page keeps its server-rendered snapshot and still has to be reloaded. The write path is unchanged: a saved change already reaches the group, as the message `{"type": "attendance_change", "data": {"key": <attendee_key>, "name": <label>, "type": "ENTER"|"LEAVE"}}`.

## Admin
`attendance/admin.py` registers `AttendanceEvent` with a collapsed `TabularInline` of its changes, and `AttendanceChange` on its own. `NonMemberAttendee` is not registered, so there is no admin page that creates a guest: those rows come from the public form, and there is nothing for an editor to maintain. `AttendancePoll` is not registered either: the editor meets it as the **Närvarokrav** inline on the poll page, which `polls/admin.py` adds behind `apps.is_installed('attendance')` together with the `Närvaroevenemang` column in the poll list (`docs/admin/polls.md`). That same block is where `present_count()` has its only caller outside the tests: an attached poll's change page reads the meeting's headcount beside the number of votes, both as read-only fields, because the person running the vote is comparing the two. The event changelist lists the title, the times and the guest switch, filters on the switch and offers a start-date drill-down, searches title, description and slug, and opens on the newest event, because the workflow is to find one event and open its overview page. It also carries a **Rapport** button on every row, added to `list_display` and dropped again by `get_list_display()` for a reader without the permission, which is the per-row pattern `events/admin.py` and `billing/admin.py` already follow (`docs/dev/events.md`, `docs/dev/billing.md`); the button opens the report described next. The change changelist lists the time, the event, both kinds of attendee and the type, filters on the type and the event, searches the event title and the attendee names, and opens newest first. `core/admin_ui.py` carries an Attendance group for the Unfold sidebar holding both changelists, so an editor on a site with `USE_UNFOLD` on can reach them from the sidebar; each link drops out when its permission or URL name does not resolve, which is what keeps the group off an association that does not install the app.

## The post-meeting report
`AttendanceEventAdmin` carries one page that answers what happened in a room: who came and went, how many were there, the polls held there and how they turned out, and a way to take all of it away as a CSV or on paper. The editor-facing side of that page is `docs/admin/attendance.md`. It is the app's only `get_urls()`, and its three routes sit under `admin/attendance/attendanceevent/<id>/report/`, each wrapped in `self.admin_site.admin_view(...)` and each re-checking its own permission, following `billing/admin.py` and `events/admin.py` (`docs/dev/billing.md`, `docs/dev/events.md`).

| URL name | Path | What it serves |
| --- | --- | --- |
| `attendance_event_report` | `<id>/report/` | the page |
| `attendance_event_report_timeline_csv` | `<id>/report/timeline.csv` | the timeline, one row per change |
| `attendance_event_report_polls_csv` | `<id>/report/polls.csv` | one row per poll per choice |

An unknown id is a 404 on all three, and `admin_view` has already established that the reader is staff before any of them runs. The page itself requires `attendance.view_attendanceevent`, asked through `self.has_view_permission(request)` so a reader holding the change permission gets in too, and a reader without it gets a 403 rather than a link. The polls are behind a second and separate permission, `polls.view_question`. Without it the page prints one muted line where the polls would be, but only when the meeting actually has polls, and the poll CSV answers 403. The rest of the page, the timeline download included, needs no poll permission.

The numbers are four. How many were present at the end is `present_at_end(event)`, and it has two readings. A meeting that recorded an `end_datetime` is read at that moment, `present_count(event.end_datetime)`, so a change logged after the end is not part of the number. A meeting without one is read at its last recorded change rather than at the clock: `present_count()` at the newest `AttendanceChange`'s own timestamp, and 0 when the meeting has no changes at all. The number has to be stable because the report is a historical document: an answer read at "now" is whoever is in the room when the page is opened, which moves with every later check-in and is a different number on a page that has already been printed or filed. `has_end_datetime` in the context is which reading the page was given, and the template labels it **Närvarande vid slutet** or **Närvarande vid sista ändringen**. It is a function of its own rather than an inline call so that the PostgreSQL-only tests can hold that exact number against `present_attendees()` where the distinct query exists. The peak, the largest number in the room at any one moment, is `peak_present_count()`, which walks the changes in timestamp order and keeps a set of who is currently in, because nothing in the database answers the question portably: it is not a column, and the window functions or `DISTINCT ON` that could answer it do not run on SQLite (see The PostgreSQL-only presence query). The changes are already loaded for the page's table, so the replay costs no query of its own. How many distinct attendees ever arrived is the number of distinct keys among the `ENTER` rows, so somebody who left and came back counts once. The fourth number is simply how many change rows the meeting has.

The page has one `h1`, the meeting's title, and the view deliberately leaves `title` out of the context: the admin base template renders that key as a heading of its own above the content, so setting it would print a second one. The page's own name is in the template's `title` block and in the subtitle under the `h1`.

The timeline is that same list, oldest first, as a table of local time, attendee name, arrival or departure, and whether the row is a member or a guest. It costs one query: `select_related("user", "non_member")` for the names, and an explicit `order_by("timestamp", "pk")` because the model orders newest first. A name comes from `AttendanceChange.attendee_name`, which is `attendee_label()` and is the name the overview list shows, so a guest reads the same in both places. The arrival or departure is `get_type_display()` translated again with the `left/entered in general` context, which is what the event page's change log does with the same string, and the kind is a column of its own rather than the `(icke-medlem)` marker `NonMemberAttendee.__str__` appends. `present_attendees()` is never called here: it does not run on SQLite, and the page wants no list of names, only the count.

Each poll attached to the meeting gets a section: the question text, whether voting has been ended, one row per choice with its votes and its share, and then three numbers beside each other, each with a label of its own. **Röstsedlar** is `get_total_votes()`, the number of ballots. **Röstande** is `voters.count()`, the members who voted, so a vote from an anonymous visitor on a poll open to anyone is not in it. **Närvarande** is the headcount the report printed higher up, repeated so a reader can see how much of the room answered. The three can legitimately disagree, which is why the page says why where they are shown: a multiple-choice poll lets one voter cast several ballots, and a poll open to anyone lets one member vote repeatedly. A percentage is guarded against a total of zero, because `get_vote_percentage()` divides by the total and raises `ZeroDivisionError` rather than answering 0 when nobody has voted. Choices are ordered by primary key, because `Choice` has no `Meta.ordering` of its own.

The two downloads follow `billing/admin.py`: an `HttpResponse` with `content_type="text/csv"` and a `Content-Disposition` header, written with `csv.DictWriter`. Three things differ from that precedent, all of them deliberate. The delimiter is a semicolon rather than the csv module's comma, because the reader is a Swedish association admin opening the file in Excel, where the comma is the decimal separator; `billing/admin.py` keeps the comma. A UTF-8 BOM (`\ufeff`) is written as the first thing in the body, so Excel reads the file as UTF-8 instead of the local codepage and the "å", "ä" and "ö" in a name survive. And every queryset carries an explicit `order_by`, because the billing export has none and its row order is undefined.

The files are named from the slug and the meeting's local start date: `narvaro_SLUG_YYYY-MM-DD.csv` and `omrostning_SLUG_YYYY-MM-DD.csv`. The slug is ASCII because the field sets `allow_unicode=False`, while the title is not, and a filename travels through mail clients and filesystems that a header value does not. The header rows are `Tid;Deltagare;Ändring;Typ` for the timeline and `Fråga;Val;Röster;Andel (%);Röstsedlar;Röstande;Närvarande` for the polls, and the timeline's times are local and written `YYYY-MM-DD HH:MM` so a spreadsheet column sorts. The ballot count, the voter count and the headcount belong to the poll rather than to the choice, so they repeat on every row of that poll: that is what leaves a row readable after it has been sorted away from its neighbours. A poll with no choices contributes no row at all.

`static/common/attendance/css/report.css` is the first print stylesheet in this repository, and it is small on purpose. Its `@media print` block hides the admin chrome (header, user tools, breadcrumbs, sidebar, footer and the page's own download buttons), keeps a table row, a list item and a heading from being split across two sheets, and repeats a long table's header row on every sheet. It does not paginate the report, add a running header or footer of its own, or produce a PDF; the browser's print dialog does the rest. The template links it from the admin base template's `extrastyle` block, which both the stock admin and Unfold define.

## Migrations
The branch has one `0001_initial`, regenerated from the complete current model state while the app is still unreleased. It creates all four tables (`AttendanceEvent`, `AttendanceChange`, `NonMemberAttendee` and `AttendancePoll`), the `foreign_keys_ok` check constraint and the case-insensitive `unique_non_member_name_ci` constraint, with the current `allow_non_members=False` default and the code-period validator. Because `AttendancePoll.question` points at `polls.Question`, Django makes the migration depend on `polls.0006_remove_question_published_question_published_time`; on an association without `attendance`, this migration is never loaded.

The migration does not copy, merge or otherwise move existing rows. In particular, a database that still contains separate guest rows whose names differ only by case cannot apply the new unique constraint until those rows are reconciled. The app has not been released, so this branch does not attempt an automatic merge that could rewrite attendance history.

A local database that ran an earlier revision of this branch has migration records for files that no longer exist. Dropping tables alone is not enough: `migrate` sees the old attendance rows in `django_migrations` and will not run the new initial migration. For disposable development data, remove the attendance tables and their `django_migrations` rows together, or use `date-cleaninit`, which recreates the database. Back up any data you need first. Once this flattened history is released, new behaviour gets ordinary forward migrations; do not rewrite it.

Both run with `core.settings.test`, which installs the DaTe app set, uses in-memory SQLite and an in-memory channel layer. `attendance/tests.py` holds 205 tests: the models (including the poll-to-meeting link, its cascades and the one-to-one), the attendee keys and entries, the TOTP code and its rotation, the presence transitions and the headcount (`PresentCountTests`, which is the portable half of the presence tests), the report's number with and without an end (`PresentAtEndTests`, which pins that a meeting without one is read at its last change whatever the clock says), the check constraint, the case-insensitive guest identity and the constraint behind it, the form, every view status code and access rule, the report page and its two downloads, the broadcast and the consumer. the detail tests pin that the change log does not cost a query per row, that the attendance heading carries the number of attendees the page was given, that the two field errors are tied to their inputs, and that `next` is rendered into the form only when it is given and only when it is local, that it survives a wrong code, a lockout and a conflict, and that a successful check-in lands on it; the index tests also pin the day-long listing of a meeting without an end and that the meeting's own page outlives it; and the detail tests pin the name cookie, meaning the attributes it is set with on a successful guest change, that the value is ASCII enough for a `Set-Cookie` header and survives a name outside latin-1, that neither a member's change nor a refused attempt writes one, that a GET prefills the box from it and reads presence for the remembered name, that a name with no row creates nothing, and the login redirect a members-only meeting gives an anonymous visitor with its `?code=` preserved in `next`; the consumer tests pin the connect snapshot, the rejected connection for a slug that does not exist, the trailing-slash route, and that a staff member whose group membership is removed mid-connection gets no code and a closed socket; Routing is covered separately by `core/tests/test_url_route_parity.py`, which asserts that `date` exposes the `attendance/` prefix and that `attendance-index` reverses for `date`; that is the test to extend when another variant mounts the app.

### The PostgreSQL-only presence query
`present_attendees()` calls `.distinct("user", "non_member")`, which compiles to PostgreSQL's `DISTINCT ON`, and it loads the attendee names with `select_related`, so a page costs one query rather than one per attendee (the PostgreSQL-only test class pins that count). SQLite does not implement the distinct: evaluating the queryset raises `NotSupportedError`, and the detail and overview views both evaluate it on every request through `get_ctx`, so on SQLite those two pages raise rather than render. Two things follow. `PresentAttendeesTests` carries the only direct tests of that method and is guarded the way `events/tests.py` guards its concurrency tests, with `@unittest.skipUnless(connection.vendor == "postgresql", ...)`, so it is skipped in CI. And because a render of either view would raise on SQLite, the view tests patch `AttendanceEvent.present_attendees` to an empty list; the transitions it computes are covered portably through `is_attendee_present()` and `was_attendee_present()`.

`present_count()` is what makes "how many are in the room" available on every backend. It answers the list's question with the same newest-change-per-attendee rule, but it orders the rows by `timestamp` descending and keeps the first row per attendee in Python, so the distinct clause is never used and one query is enough however many changes the event has. It exists beside `present_attendees()` rather than replacing it because only the list knows the names, and only the count is portable. `PresentAttendeesTests` asserts that the two agree over several mixed change logs, at the timestamp asked about and at moments around it, which is the test that keeps the portable count honest against the real query, and its newest case does the same for `present_at_end()` at a meeting that has an end, the number the report prints; on SQLite that class is skipped, and `PresentCountTests` covers the transitions through the count alone, including the one-query cost, while `PresentAtEndTests` covers the report's other reading, a meeting with no end, portably. That newest case calls `present_at_end()` rather than rendering the report through the test client: the client's session and middleware hit the closed-connection problem described below on PostgreSQL, and the helper is what produces the number either way.

### Running the file against PostgreSQL
The file is written for `core.settings.test`. On PostgreSQL it cannot run in one go, and the cause is worth writing down precisely, because it is not this app's code. `channels`' `AsyncConsumer` calls `close_old_connections()` before it dispatches each message (`channels/consumer.py`), and Django's `close_if_unusable_or_obsolete` drops the connection whenever autocommit is off, which inside a `TestCase` it always is. PostgreSQL is then left with a connection closed inside a transaction, and every later query in the process fails with "connection already closed": the websocket tests after the first one, and every class that runs after them. SQLite never takes that branch, because its backend always reports autocommit, which is the whole reason the suite is green there. `AttendanceConsumerTests` also patches `AttendanceEvent.present_attendees`, which the connect snapshot evaluates and which SQLite cannot run at all.

Two remedies were tried and rejected. Giving `AttendanceConsumerTests` `TransactionTestCase` breaks those tests on SQLite and does not help PostgreSQL. Reconnecting in `tearDown` breaks them on both, because `tearDown` runs before Django rolls the test's transaction back. `PresentAttendeesTests` does pass against PostgreSQL when it is run on its own, which is how the presence query is checked there. A real fix belongs to the test harness rather than to this app: the consumer tests have to run outside a `TestCase` transaction on a backend that reports transaction state, or in their own process.

### What is not covered
The six `PresentAttendeesTests` cases never run in CI, because CI uses SQLite, so the one method that only works on PostgreSQL is verified only when somebody points the suite at PostgreSQL, and the agreement tests added beside it (two of which hold `present_count()` against it, and the sixth of which holds the report's printed number against it) are skipped with it, so what CI pins about the headcount is `PresentCountTests` alone. Neither script has automated coverage: the QR flow, the code countdown, the snapshot merge, the list updates and the headcount in `#present-count` in `overview.js` are checked by hand, and the tests cover the broadcast payload, the absolute event URL the view hands the QR code, and the markup the script reads (including the `#present-count` element and the number the server renders into it), rather than what the DOM does with them.

## Adopting the app in another association
1. Add `'attendance'` to that variant's installed apps (`get_installed_apps([...])` in `core/settings/<variant>.py`). `core/settings/date.py` is the worked example.
2. Add the `attendance` route key to that variant's `build_urlpatterns(...)` call. `core/urls/date.py` is the worked example. Unlike `booking`, the key is not gated on a capability, so a variant that wants an off switch has to add one.
3. Run that variant's migrations so the tables exist.
4. Add that variant to `EXPECTED_PREFIXES` and `EXPECTED_URL_NAMES` in `core/tests/test_url_route_parity.py`, or the parity test fails.

The templates under `templates/common/attendance/` and the scripts under `static/common/attendance/js/` are shared, so nothing else is required; an association-specific override follows the usual `templates/<association>/` rules in `docs/dev/templates.md`. No module under `attendance/` outside its tests reads `PROJECT_NAME`, `STAFF_GROUPS` or a content variable, so the app itself needs no configuration beyond being installed and routed. One requirement is new: `AttendancePoll.question` points at `polls.Question`, so `polls` has to be installed as well. Every association installs `polls` today, so this only binds a future one.

## Non-member identity
`NonMemberAttendee.name` is unique across the whole table, and the check-in view resolves a typed name case-insensitively on a trimmed value: `get_or_create(name__iexact=<trimmed name>, defaults={"name": <trimmed name>})`. A guest who types `david dahl` after somebody typed `David Dahl` therefore lands on the same row, and `  David Dahl  ` does too. The first spelling stays what the row holds, and it is what the change log, the list and the report show, because the create only runs when nothing matches and the value it stores is the trimmed one. Case and leading or trailing whitespace are all that is folded. A nickname or a different surname is still a new row, so two different people who type the same name share one row for every event, and the change log cannot tell them apart. That is accepted because the app is a list of who was in the room, not an identity system: a guest has no account to key on, and splitting the name into first and last name would not change anything, since the collision is on the name either way. A real fix would take something that distinguishes people, an address or a per-event record, which is more than this list needs. The practical consequence is in the admin guide: ask guests for a name that is theirs alone.

`unique_non_member_name_ci` in the model's `Meta.constraints` is the same fold in the database, and it is there because the lookup alone cannot stop two devices racing: both look, both find nothing, both insert. `unique=True` on the field stays and is the exact-name constraint that already existed, so the table carries both. The two backends fold differently and that difference is worth knowing. PostgreSQL folds Unicode case, so `Åsa` and `åsa` are one attendee in production. SQLite folds ASCII only, so the suite's database treats those two as different names, and the constraint test therefore uses an ASCII pair, `David Dahl` and `david dahl`. The check-in lookup follows the same split, because on SQLite Django implements `iexact` with an ASCII-only `LIKE`, so the suite cannot pin the Unicode case in either half.

The detail view's name cookie changes none of this: it prefills the name box with the name typed last time and looks that name up case-insensitively, so the guest who typed `david dahl` still gets the presence line of the `David Dahl` row.

## Deleting a member
`AttendanceChange.user` is `on_delete=CASCADE` on purpose, and it matches `polls.Vote.user` and `members.SubscriptionPayment.member`: deleting a member removes their own attendance changes with their account. An erasure request should not leave a trail of "this person attended these meetings" in a table nobody thought about. What outlives a member is the minutes, not this table. Nothing marks a row as belonging to a deleted account, and no report survives the deletion, so attendance history that has to outlive an account must be exported or recorded elsewhere first. Deleting an event cascades in the other direction: the event's changes go with it, while a guest's name row stays, because it is shared between events.

## Risks and limits
- Staff access is group membership, so everyone in `styrelse`, `admin`, `fotograf` and `rösträknare` can see the code and the change log. The app has no permission of its own that narrows the overview page; only the admin edit pages use model permissions.
- The attendee list on the event page is public to anyone who can open the page, including guests' names. Only the change log is behind `user.is_staff`. If a meeting's attendee list should not be public, that is not a setting today.
- The code is a proof of presence, not a credential: six digits, displayed to the room. The attempt limit that guards it is a session counter, so a client that discards its cookie is not bounded by it.
- The remembered name is a convenience, not an identity: it prefills one input and answers whether that name's row is present. It grants nothing a typed name did not already grant, so editing or clearing it costs a guest nothing but retyping.
- An ended event is still reachable and still accepts check-ins, because nothing reads `has_ended`, and the same is true of a meeting without an end a day after it started, which the public list no longer shows. Anyone who still has the link or the QR code can check in.
- The attendee list on the event page is a snapshot from the request. Only the staff overview page is live, because `overview.js` is the only client that consumes the broadcast.
- Deleting a change row in the admin changes who counts as present, because presence is read from the newest row.
- The suite runs on SQLite, so the six `PresentAttendeesTests` cases, the only tests of `present_attendees()`, are skipped in CI and the method's behaviour on PostgreSQL is verified only when somebody runs them there. The agreement tests beside them are skipped with them, so only `present_count()` is exercised in CI, and the report's printed number is held against the real query only on PostgreSQL.

## Extending
- Consume the `attendance_change` broadcast from `detail.js` too, so the event page's own list is live as well; the staff overview page already does, and both would read the same payload.
- Give the consumer tests a database setup that survives the connection `close_old_connections()` closes, so the whole file can run against PostgreSQL and not only on SQLite.
- Add pagination or a date filter to `AttendanceEventsView` if the event list grows.
- Move the attempt limit off the session if guessing ever matters more than it does now. That needs a key the client cannot discard, which means deciding how to treat client addresses behind the ingress first.
